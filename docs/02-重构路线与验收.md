# 学历证书存证系统：重构路线与验收

本轮目标是在 Ubuntu 上得到可以真实操作、用于授课录屏的完整系统。先完成系统和操作验收，再制作授课 PPT。

Ubuntu 项目目录统一为：`/home/wsc/degree-cert-system`。已有长安链环境保留在原位置，通过配置连接；不覆盖旧链、旧配置或原始资料。

## 1. 已确认的旧系统事实

- `code.zip` 保存了更完整的正式答辩版，包括模块化 Flask 后端、16 个模板和 Go 合约，**作为本次重构的主要业务参考**。其数据路线是链下保存证书全文，链上保存哈希、状态及存证信息。
- 正式版包含登录、颁发、查询、核验、撤销，以及版本链、批量处理和审计相关入口；有代码入口不代表所有功能已完成端到端验证。
- 正式版的核验需要重点重写：`routes/certificates.py` 用 `cert_id` 请求要求 `cert_hash` 的合约方法，随后未使用返回的链结果，仅比较输入内容哈希和本地数据库哈希。这不能证明链上存证一致；新版必须在链查询成功后使用真实链上数据作判断，链不可用时明确显示“暂无法完成链上核验”。
- 正式版固定了 `/home/glxx` 等路径、合约名 `test6`，并通过 `sudo` 调用 CMC。重建时需要移除旧机器绑定，按当前环境配置普通用户可用的链访问方式。
- 正式版 `contracts/go.mod` 声明 Go 1.20、`contract-sdk-go/v2 v2.3.2`，并以 `replace` 指向 `../contract-sdk-go`；压缩包缺少该 SDK 目录，也没有 Python 依赖清单。因此仍不能直接复制运行。
- 两份散落“源代码”目录的 14 个文件完全一致，属于简化教学参考：单文件 Flask、SQLite 仅存账号、证书全文直接上链。其 `verify.html` 没有对应后端/合约入口。这个结论只针对简化版，不能套用到 `code.zip` 正式版。
- 指导书使用长安链 2.3.4、SmartIDE 编译及 `DOCKER_GO` 部署；简化合约引用 `chainmaker/sdk`、`chainmaker/sandbox`、`chainmaker/pb/protogo`，与正式版的模块布局不同。链版本、SDK 版本和 Go 版本必须分别确认，不混用两套构建方式。

以上是资料审查结论；Ubuntu 实际版本、节点及 Docker VM 状态仍需环境检查确认。

## 2. 本次实现约定

采用 Flask/Jinja + SQLite + CMC + Go `DOCKER_GO` 路线。SQLite 保存账号和链下证书全文，链上保存证书内容哈希、状态及必要存证信息；查询和核验结合两侧数据。前端静态资源随项目保存，避免录屏依赖外部样式 CDN。依赖、链地址、身份路径、合约名均写入明确配置；Python 使用项目独立虚拟环境。

先跑通“颁发—查询—内容核验—撤销—再次核验”的真实链闭环；版本链、批量处理和审计功能在此基础上分阶段恢复。以正式版业务为参考，不把未验证的旧入口直接标记为完成。

核心改进：

1. **真实回执。** CMC 退出成功不等于合约执行成功；统一检查交易码、合约结果码，解析实际返回内容，页面展示交易 ID、执行状态及明确错误。
2. **稳定内容哈希。** 明确不可变学历字段、字段顺序、编码、空白和日期规则，对规范化内容计算 SHA-256。状态、撤销原因、撤销交易和哈希自身不进入内容哈希；撤销前后内容哈希保持一致。
3. **真正的内容核验。** 用户提交待核验的证书内容，按同一规则计算哈希，与链上原始内容哈希比较。展示“内容一致/不一致”和“有效/已撤销”两个独立结果。只按 ID 查到一条记录属于查询，不构成内容核验。
4. **数据一致性与多证书索引。** 证书 ID 关联链下全文和链上存证；学生索引关联该学生的多张证书 ID。同一学生再次颁发、撤销其中一张时，其余记录和查询结果不被覆盖。链写入失败不能留下“已颁发”的本地假记录；对等待确认的交易保存明确状态及可追查信息。
5. **两层权限。** 保留网页角色限制，并在合约中校验经认证的交易发送者身份。具体 SDK 的发送者接口、组织/证书映射及身份配置待实机确认；不能只信任表单中的操作者，也不能把合约创建者当作当前发送者。
6. **适合演示。** 中文字段、证书卡片、列表、状态和错误提示；账号、会话密钥和业务配置分离。演示使用虚构学生数据。

## 3. 分阶段实施及验收

| 阶段 | 要做的事 | 完成标准 |
| --- | --- | --- |
| 1. 环境确认 | 运行首次环境检查，确认 Ubuntu、Go、Python、Docker、CMC、链与 SDK 路径 | 拿到报告，确认缺什么、复用什么；**当前阶段，待 Ubuntu 反馈** |
| 2. 链连接与构建基线 | 按实际版本整理配置，确认 Docker VM；建立匹配的合约 SDK/模块和打包方式 | CMC 能读取实际链信息；最小合约可以编译、部署和调用，留存真实回执 |
| 3. 合约重构 | 实现哈希存证、查询、撤销及发送者权限；确认索引设计，统一结构化返回 | CMC 可验证真实状态变化；内容哈希不随撤销变化，无权限身份被拒绝 |
| 4. 后端联调 | 建立账号及证书全文库、规范化哈希、多证书索引、配置加载、CMC 适配层与错误处理 | 两侧数据正确关联；核验能识别内容改动；链失败或超时不显示成功，不盲目重发 |
| 5. 核心前端完成 | 接入核心业务页面，完善中文交互和本地静态资源 | 在 Ubuntu 浏览器完成核心闭环，无需手工读 Base64 或原始 JSON |
| 6. 扩展功能恢复 | 分别联调版本链、批量处理和审计入口 | 旧版本内容和存证可追溯；批量逐条展示结果；审计与实际操作对应，每项单独验收 |
| 7. 整体验收 | 用虚构样例走完整流程，整理启动、停止和恢复说明 | 重启应用后两侧数据仍可关联核验；录屏操作可重复，配置与启动步骤可复现 |

阶段 1 不安装软件、不启停节点、不部署合约。收到环境报告后再确定后续命令，避免误用旧版本、旧用户名或不匹配的 SDK。

## 4. 必须通过的业务用例

- 高校颁发证书 A，获得实际证书 ID 和交易 ID；按 ID、学生信息都可查询。
- 使用 A 的原始学历内容核验，结果为内容一致、证书有效；修改专业或毕业日期后核验，结果为内容不一致。
- 为同一学生颁发证书 B；学生查询同时返回 A、B，列表无重复记录。
- 教育主管部门撤销 A，保存原因及撤销交易 ID；A 内容哈希不变，原始内容核验仍一致，但有效性显示已撤销；B 保持有效且可查。
- 再次撤销 A、查询不存在的证书、提交缺失或非法字段时，返回明确失败。
- 查询角色无法颁发、撤销或读取受限全量列表；绕过网页直接用无权限链身份调用，也被合约拒绝。
- 节点不可用、合约执行失败或交易等待超时时，页面不误报成功；不确定交易先按交易 ID 查结果。
- 链下证书内容被改动时，核验提示与链上哈希不一致；链下全文缺失时明确说明无法完成内容核验，不因链上存在证书 ID 就显示内容可信。

扩展阶段另行验收：新版本保留旧版本的原始内容哈希及关联；批量部分失败时成功、失败、待确认逐条可辨；审计记录与真实操作及交易对应。核心闭环完成不等于这些扩展已经完成。

仅页面可点击、仅模拟数据返回或仅 CMC 进程退出正常，都不算整体验收通过。完成标准是浏览器操作与真实链上状态一致，并能说明每次写入对应的交易。

## 5. 每阶段交付方式

代码和操作文档放在本项目目录，原始资料保持不变。每次给出需要复制到 Ubuntu 的文件、准确目标路径、执行命令和预期结果；根据上一阶段的实际反馈推进，不要求一次执行整套尚未验证的部署命令。
