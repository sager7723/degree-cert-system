# 录屏演练流程

完成第七步备份与整机重启验收后使用本说明。此时先录制系统操作素材，授课 PPT 后续整理。

## 准备

使用虚构学生资料。保留 A/B 两张已有证书作对照；每次演练或正式录屏使用新的自动证书编号，不复用已签发编号。记录本次证书编号以便切换账号后查询。

关闭账号密码文件和身份材料窗口，浏览器保持合适缩放，鼠标放在左栏内可滚到底部退出。启动链和网页的终端保持运行，录制区域选择 Ubuntu 浏览器。

## 分镜建议

| 片段 | 账号与操作 | 应拍到的证据 |
| --- | --- | --- |
| 1. 系统概览 | uni_admin 登录工作台 | 机构身份、真实合约连接状态、证书列表 |
| 2. 签发 | 使用自动编号签发一张虚构证书 | 原文、确认结果、签发交易 ID、内容摘要 |
| 3. 核验原文 | 从详情进入核验，直接提交 | 内容一致、链上有效 |
| 4. 识别改动 | 只改核验表单的专业，再提交 | 内容不一致；原证书未被修改 |
| 5. 独立查询 | 从左栏底部退出，用 query_user 登录并按完整编号查询 | 查询机构身份与只读功能 |
| 6. 监管撤销 | 退出，用 edu_admin 登录，找到该证书并填写演示撤销原因 | 撤销交易 ID、原因、链上已撤销 |
| 7. 再核验 | 核验原内容或原导出 JSON | 内容仍一致，但已撤销，不能判为当前有效 |
| 8. 留痕 | 查看对应账号交易记录，再查 B | 原交易可追溯，B 仍有效 |

无需为录屏删除数据库、重置链或重新部署合约。表单提交后等待页面返回；遇到待确认状态，使用交易记录的“查证原交易”核对。

## 后续讲解结构

1. 应用设计：高校、监管、查询三类角色分别负责什么；为什么需要链上记录。
2. 数据设计：按证书编号区分同一学生的多张证书；链下全文、链上摘要与状态如何关联。
3. 核验逻辑：规范化 JSON → SHA-256 → 合约核验；内容匹配与证书有效是两个判断。
4. 代码路径：Flask 路由 → Registry → CMC → Go 合约 → 查询已入块交易 → SQLite 确认。
5. 改进点：权限检查、原交易查证、重复提交控制、撤销留痕、整机恢复。

以上是授课素材的组织方向，本阶段不生成 PPT。
